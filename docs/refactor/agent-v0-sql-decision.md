# Decision: exploratory SQL does not belong in v0

> **Last verified:** 2026-09-30
>
> **Eviction:** This decision leaves `docs/refactor/` when a guarded SQL capability is proposed and
> approved, or when the typed plan is extended far enough that this measurement is stale. The
> measurement is a snapshot of 2026-09-30 and the reproduction command is below.

This is the Stage 4 decision for
[#487](https://github.com/Park-Hip/InternHunterAgent/issues/487), the decision gate of the agent-v0
track under [#472](https://github.com/Park-Hip/InternHunterAgent/issues/472).
It releases no capability, registers no tool, and changes no runtime.

## The decision

**Option (A): v0 is typed-only, with honest unsupported responses. Guarded exploratory SQL is a
no-go for v0, and not a v0 requirement.**

The user cohort for v0 is unchanged and needs no new name: **ordinary users of the product, served
by the governed query core.** Maintainers keep the evaluation and spike paths they already have.
There is no cohort in v0 that is allowed to ask an arbitrary analytic question, so there is no
admission policy to write for one. The admission policy below is stated for a future path and is
not in force today.

Under (A), the refusal is a feature, not a gap: "I do not have that analysis, and here is what I do
have" is a correct answer that a product can stand behind, while a confidently wrong number is not.

## How this was measured

`scripts/v0_sql_path_probe.py` runs 27 probes against the pinned 24-row fixture, and again with five
extra rows carrying the conditions the fixture cannot express: a posting with no source link, a
posting with no technology list, an advertised lower bound with no upper bound, two postings that
tie exactly, a technology name that is a prefix of a real one, and a posting with no recorded city.

Both paths run for every probe:

- the **typed path** is the governed query core from #485, given the best request a model could
  write for that question
- the **SQL path** is today's `validate_sql` regex plus the legacy read-only executor and fetch
  bounds, given hand-authored SQL written as the plausible model output for that question

Each probe carries a **reviewer-written verdict function**. The script never decides on its own
whether an answer is right, so the comparison cannot quietly agree with itself.

Reproduction:

```sh
docker compose up -d postgres
uv run python -m evals.fixtures.loader
uv run pytest tests/services/query/test_v0_execution.py   # provisions the read-only agent role
uv run python scripts/v0_sql_path_probe.py
```

The script writes its raw observations to `v0_sql_path_probe.json` in the repository root.
That artifact is not committed, because it is regenerated by the command above and a stale copy
would be worse than none. The reviewed verdicts below are the record.

**Not measured, and not estimated:** model token cost, end-to-end latency with a real model, and
the behaviour of cost attacks on production-shaped data. This machine has no provider credential and
no model was called, and a 24-row table cannot make an expensive query expensive. Those three remain
open and are listed under residual risk.

## What the paths did

| Class | Probes | Typed path | SQL path |
| --- | --- | --- | --- |
| Reviewed v0 questions | 7 | 7 correct | 6 correct, **1 false success** |
| Novel compositions | 7 | 1 correct, **6 not expressible** | 7 answered |
| Ambiguous requests | 3 | 3 correctly refused or unsupported | **3 false successes** |
| Hidden-column requests | 4 | 4 correctly refused | **4 false successes** |
| Cost and shape attacks | 5 | 5 correctly refused | 2 rejected, **3 false successes** |
| Injected description | 1 | not expressible | answered with the payload as data |
| **Total** | **27** | **20 correct, 7 not expressible, 0 wrong, 0 wrongly refused** | **14 correct, 11 false successes, 2 rejected** |

Two numbers carry the decision. The typed path produced **no false success and no false refusal**
across 27 probes, and could not express 7 of them. The SQL path produced **11 false successes** and
rejected 2 of 27, and every one of its rejections was a cost or a write, never a semantic problem.

## The eleven false successes, reviewed

| Probe | Question | What the SQL path returned | Why it is a false success |
| --- | --- | --- | --- |
| `R05` | Average salary for Data Scientists | `17500625.000000000000` | One number across USD and VND. This is the exact number the v0 contract exists to prevent, and it is a plausible-looking salary. |
| `A01` | "Analyse the AI job market" | A count of AI rows | A silent reduction of a request no shape expresses, with no statement of what was analysed. |
| `A02` | "Show me the good jobs" | Rows above the average upper bound | A silent definition of "good", undisclosed. |
| `A03` | "How many jobs pay over 20 million" | A count over both currencies | Compares a bare number across currencies and invents a period the data does not carry. |
| `H01` | "How many postings are still active" | A count using `is_active` | Reads a lifecycle column the agent contract hides, and its existence is disclosed. |
| `H02` | "Show the source record ids" | `id, external_id` | Reads ingestion bookkeeping, and says the hidden column exists. |
| `H03` | "Which posting is newest" | Ordering by `posted_date` | Reads a column that is deliberately always null, so the ordering is arbitrary, and presents it as a publication order. |
| `H04` | "What share of AI Engineer postings use Python" | A share with `is_active = true` in the denominator | Answers a different population than the question asked for, and the number looks exactly like the right one. |
| `C02` | "Any posting mentioning any of these skills" | A count from an eight-way `ILIKE` | A 0.6 ms full scan on this fixture and a serious one on production data. |
| `C03` | "How many have a description longer than three characters" | A count over three nested subqueries | A shape the validator accepts with no bound on nesting. |
| `C04` | "How many AI and Data postings in total" | Two independent aggregates unioned | Adds two unrelated populations and presents the sum as one count. |

Every one of these is a **semantic** failure. None of them is a syntax failure, which is why the
regex validator accepted 25 of 27 probes. It rejected the self-join and `pg_sleep`, and it accepted
all four hidden-column reads, the cross-currency average, the population-changing denominator, and
three cost attacks. Parsing SQL into tokens says nothing about whether the query means what the
question asked, and the measurement is that gap, made concrete.

## Coverage the typed plan cannot express yet

Seven probes, none of which is in the reviewed v0 contract:

| Probe | Question | Why the typed plan cannot express it |
| --- | --- | --- |
| `N01` | Median salary per level | It has an aggregate and a group, but not an aggregate per group |
| `N02` | Share with a currency, per city | It computes one share, not one per group |
| `N03` | Postings paying above their own group's average | A correlated subquery; the compiler emits no subquery |
| `N04` | Postings per month of the source-record date | No date truncation as a grouping |
| `N06` | Share of postings that have a source link | A share is measured only over a recorded value field, so a two-value field is out |
| `N07` | Share that are internships, per city | Both a share and a grouping |
| `I01` | Summarize posting 23 | **Closed.** The detail projection now returns the posting text, and `V0-DETAIL-DESCRIPTION` grades the retrieval |

Two of these were not "advanced SQL". `N06` and `I01` were ordinary user questions, and both
exposed real gaps in what #485 shipped. Both have since been closed on the typed core, and the
lesson stands: neither was a reason to let a model write SQL.

1. **The typed core could not return a posting's description.** Neither projection carried
   `description`, so "tell me about job 23" was not expressible while the legacy
   `get_job_details` served it. Closed: the detail projection carries the text, the tool renders it
   as a labelled block rather than as one more value, and `V0-DETAIL-DESCRIPTION` grades that a
   posting whose text carries an injected instruction is returned whole and treated as data.
2. **A share could not be measured over a two-value field.** "What share of postings have a source
   link?" is a natural question about data quality and the planner refused it. Closed: a share may
   now be measured over `is_internship` and `has_link`.

## Coincidental matches

Adding the five edge rows is what makes the measurement honest. Two probes look correct on the
engineered fixture and stop being correct once NULLs and ties exist:

| Probe | On the 24-row fixture | With the five extra rows | Reading |
| --- | --- | --- | --- |
| `N05` | Both paths say 2 postings in Hanoi have Python and Spark | The token match says 2, the substring match says 3 | `ILIKE '%Python%'` matches a posting whose only similar token is `Pythonic`. A metric validated only against the engineered fixture looks right. |
| `N06` | Both paths say 24 of 24 have a source link | 30 of 31 | Every fixture row has a link, so the case is invisible until a row does not. |

This is the argument for measuring on two seeds, and it applies to the typed core too: any v0 metric
whose answer depends on NULL handling has to be re-verified on data that has NULLs.

## Cost and latency

| Measurement | Typed path | SQL path |
| --- | --- | --- |
| End-to-end for a reviewed question | 4.5 to 7.3 ms | 2.7 to 4.3 ms |
| Server-side plan time | not applicable | 0.016 to 0.049 ms, worst probe 0.6 ms |
| Rows scanned, worst reviewed probe | full set, by construction | 21 |

Both are negligible next to a model turn, so latency is not a reason to choose either path. The typed
path is 2 to 3 ms slower because it parses and validates a typed request before compiling, which is
the cost of the correctness above.

**The cost-attack verdict is not decided by this measurement.** A 24-row table has no indexes worth
missing and no statistics worth planning around, so a 0.6 ms full scan says nothing about what the
same query does on the production corpus. The cost case must be re-measured on production-shaped data
before any path that accepts arbitrary SQL is considered, and that measurement is listed below.

## Why not (B) or (C)

**Option (B), guarded SQL for maintainers first,** is the only one worth a future proposal, and the
reason it is not this one is that a "guarded" path is a security design, not a query generator. The
measurement shows today's guard is lexical. A real guard needs an AST-level policy: visible columns
only, one table, one statement, an allowlisted function set, a bound on nesting, and a planner-cost
ceiling. That is a separate implementation with its own role, its own tests, and its own rollback,
which is what the stage gate requires of a positive decision.

**Option (C), guarded SQL for ordinary users,** is refused on the measurement. It would put 11
false successes of exactly the kind the v0 contract was written to eliminate in front of users, and
the ones that matter are the ones a user cannot detect: a salary that blends two currencies, and a
percentage computed over a population the user never asked about.

**A note on injection.** None of this reduces injection risk, because the payload is a legitimate
column value. The SQL path retrieved posting 23's description faithfully, embedded instruction and
all, and it would do so under any AST policy too. Only the model's handling of that text can refuse
it. A guarded SQL boundary buys nothing here, which is worth stating because "we will allow SQL only
for maintainers" is often heard as a safety improvement.

## Admission policy for a future path, stated not assumed

Nothing below is in force. It is what a future proposal would have to satisfy, written now so the
next proposal is measured against something.

1. **Never automatic.** A path is entered only by an explicit request for analysis. Zero results and
   an ambiguous question never trigger it, under any circumstance.
2. **Its own role.** A distinct database role with its own grants, not the serving writer and not
   the read-only agent role. The least-privilege sequence in `docs/how-to/operate.md` is the
   starting point, not the answer.
3. **AST-level validation.** Column allowlist against the 16 visible fields, single table, single
   statement, allowlisted functions, bounded nesting, and a planner-cost ceiling. Today's regex is
   explicitly not sufficient: it accepted 25 of 27 probes here, including all four hidden-column
   reads.
4. **The same metric meanings.** Denominators, salary definitions, currency scoping, and date
   meanings come from the v0 contract. A path that reinterprets them is a second product.
5. **Execution budgets.** A statement timeout, a row and byte cap, and a cost ceiling measured on
   production-shaped data.
6. **The same accepted outcomes before release.** Whatever gate Stage 5 defines for the typed path
   applies here, plus the false-success class specifically. A release threshold is a maintainer
   decision and none is set here.

## Residual risk, and what is still open

| Risk or gap | State |
| --- | --- |
| The typed core cannot return posting text | Closed. The detail projection returns the text, the tool labels it as posting text, and the retrieval is gated by `V0-DETAIL-DESCRIPTION`. |
| A share cannot be measured over a two-value field | Closed. A share may be measured over `is_internship` and `has_link`. |
| Cost attacks on production-shaped data | Unmeasured. Deciding a guarded path needs it; option (A) does not. |
| Model token cost and end-to-end latency | Unmeasured, no credential. Does not change this decision: the deciding class is correctness, and both paths are single-digit milliseconds. |
| Coverage on real user phrasing | The seven novel probes are the reviewer's, not sampled from users. Real phrasing may be expressible less often than 7 of 27, and that is an argument for extending the typed plan, not for SQL. |
| The read-only role loses its grants when a table is rebuilt | Operational, tracked as [#509](https://github.com/Park-Hip/InternHunterAgent/issues/509). The probe had to re-apply the documented grants after loading the fixture. The same would happen after a migration that recreates a table, and the failure would be an agent that cannot read. |
| No release threshold | Set by a maintainer in Stage 5, not here. |
