# Known Issues & Risks

Living register of known issues, risks, and out-of-scope follow-ups discovered while
implementing tickets. This is the single place to record such findings — do **not** fix
them inline as part of an unrelated ticket (per `CLAUDE.md` §1: report follow-ups
separately, never fix them automatically).

## How to update
When a ticket uncovers a risk, bug, sharp edge, or deferred item:
- **Append** a bullet below (most-recent last). Keep existing entries; only remove one
  when it is genuinely resolved, and say so in that ticket's completion report.
- Note **where** it was found (e.g. "Observed during T0007.2 verification") and, when
  useful, a **candidate follow-up**.
- If the issue warrants its own ticket, still log it here and flag it as a follow-up
  ticket in the completion report.

`Repo_Current_State.md` links here instead of duplicating this list.

### Config, startup & deployment
- The repository appears to rely on import-time loading in `src/core/config.py` (module-level `settings = load_settings()`), which makes startup sensitive to working directory (the three `config/*.yaml` paths are resolved relative to CWD) and to missing env/config files. Confirmed during the 2026-07-02 pre-deploy audit. Works in the Docker path (`WORKDIR /app`, config `COPY`ed to `/app/config`), but any invocation from another CWD or without env fails at import.
- `main.py` is only a placeholder (`print("Hello…")`). **Confirmed not deploy-blocking** during the 2026-07-02 audit: `docker/Dockerfile`'s `CMD` runs `uvicorn src.api.app:app` directly and never imports `main.py`, so the stub is dead code, not the entrypoint. Candidate follow-up: delete `main.py` or repurpose it as a thin CLI entrypoint.
- **Deploy-secret checklist required before any non-local deploy** (confirmed 2026-07-02): `infra/docker-compose.yaml` (the Langfuse stack) ships upstream `CHANGEME` defaults for `SALT`, `ENCRYPTION_KEY`, `NEXTAUTH_SECRET`, Postgres/Redis/ClickHouse/MinIO passwords, and S3 keys — all `${VAR:-default}` env-overridable, safe locally, **unsafe on a public host**. Candidate follow-up (own ticket at deploy time): author a required-env `.env`/secret checklist and set every one before exposing the stack.
- `DATABASE_URL` is required and must be set in the runtime environment before starting the app.
- `config/settings.yaml` is `COPY`ed into the API image, so changing values like `agent.memory.max_messages` requires a `docker compose build --no-cache api` to take effect — a plain `--build` can reuse a cached `COPY config` layer and silently run stale config.
- ~~**[HIGH — time-boxed] Agent LLM `llama-3.3-70b-versatile` is being retired by Groq**~~ **Resolved 2026-07-04:** `config/settings.yaml:4` now pins `agent.groq.model: qwen/qwen3.6-27b` (chosen over `openai/gpt-oss-120b`, which has reported tool-calling regressions on Groq — LangChain #34155 — and is kept only as the *judge* model, where no tool calls happen). The retired `llama-3.3-70b-versatile` (Groq deprecated 2026-06-17, shutdown 2026-08-16) is no longer referenced. **Residual [LOW]:** the qwen pin has **not yet been live-validated** against the agent's tool loop — confirm `qwen/qwen3.6-27b` is a current Groq production model ID and that the agent still invokes `query_clean_jobs`/`get_job_details` cleanly **before the T0011.5 baseline run**, so the baseline measures the shipping model. A wrong ID surfaces as a `ChatGroq` runtime error, not a config error. Background: `research/deepeval-sql-agent-eval-planning.md` §11.4/§11.7 (F1).

- `load_sql_generation_prompt()` returns a plain `str` rather than a `SystemMessage` like `load_system_prompt()`, since the SQL-generation flow combines it with `load_schema_context()` text before sending it to the model.
- **`response.content.strip()` assumes string content** (mypy-flagged, 2026-07-02 audit): `src/agents/tools/query_clean_jobs.py:41` calls `.strip()` on `model.invoke(...).content`, whose type is `str | list[...]`. With Groq text replies it is a `str` today, but a list-content reply (structured/tool blocks) would raise `AttributeError`. Latent edge case. Candidate follow-up: coerce non-str content to text before `.strip()`.
- **Residual mypy type-variance (benign, 2026-07-02 audit):** `src/core/checkpointer.py:25` (`AsyncPostgresSaver` connection-pool row-type `tuple` vs `dict`) and `src/agents/runtime/middleware.py:48` (`trim_messages` `list[BaseMessage]` vs the narrower `ModelRequest.override` union) are correct at runtime — the stubs are imprecise. Left un-suppressed so they stay visible; annotate with a commented `# type: ignore[...]` if/when a fully-green `mypy` gate is wanted.
- Observed during T0006.10 verification: the agent sometimes calls `query_clean_jobs` twice in a row with identical arguments before producing its final answer (harmless — deterministic, no side effects — but wastes one round-trip). Candidate follow-up: investigate prompt/loop tuning to remove the redundant call.
- Context trimming caps only what the model sees per turn (`agent.memory.max_messages`, default `20`); the full thread keeps growing in the checkpointer by design. There is no storage-side pruning or token-based budgeting in this MVP (summarization/token budgeting are explicit non-goals).
- Observed during T0007.2 manual verification: asking a refining follow-up about an attribute that has no corresponding column in `clean_jobs` (e.g. "Which of those are remote?" — there is no `remote`/`location` column exposed in the schema context) makes the agent stall for several seconds before it works out it cannot answer, rather than recognizing quickly that the attribute isn't queryable. The eventual answer is still correct/non-fabricated, but the latency suggests the system/SQL-generation prompt could more explicitly guide the model to recognize out-of-schema attributes faster. Candidate follow-up: tune the schema-context or system prompt so the model short-circuits on out-of-schema refinements instead of spending a full reasoning pass figuring it out.
- **`posted_date` intentionally absent from agent schema** (T0009.7): `posted_date` is a column in the `clean_jobs` DDL (added T0009.1) but is never populated by the current ingestion pipeline (VietnamWorks API does not surface a reliable published date). It is deliberately omitted from `config/prompts.yaml` `schema_context` and `system_prompt` so the agent cannot query or reference it. **Verified during T0009.8, with a caveat**: asked the freshness question 3 times against the live stack ("Which of the AI Engineer jobs were posted most recently?" and the ticket's exact wording) — 2 of 3 attempts correctly declined, but 1 of 3 fabricated a specific "most recently posted" job despite having no date data at all. The schema-omission mechanism works (the column is genuinely unreachable via SQL), but the model doesn't reliably refuse to *guess* an answer from title/description context alone. Candidate follow-up: strengthen the honesty-rule wording/few-shot example for freshness specifically, or add a guardrail that detects date-like fabrication in the answer. When a source surfaces reliable publish dates, expose `posted_date` in the agent schema and update honesty rules accordingly.
  - **Reliable-time-column path (design note, 2026-07-04):** the VietnamWorks timestamps that *do* exist (`onlineOn`/`approvedOn`/`expiredOn`, per `research/job-site-comparison.md` §122) are what make a *posting* date unreliable, not their absence: `onlineOn` is a re-listing timestamp that churns whenever an employer refreshes/reposts (it's exactly what powers `order: onlineOn desc` newest-first pulls), `approvedOn` is an administrative approval time, and `expiredOn` is a future expiry — none reliably means "when this job was first posted." The trustworthy alternative is not a source date at all but an **ingestion-owned** timestamp (`first_seen_at`/`last_seen_at`, which we fully control) or an honestly-renamed `listed_on` column (with a `schema_context` description that says "last relisted — may reflect an employer refresh, not original posting"). All three depend on the **accumulate-upsert persistence planned for T0013** — today `clean_jobs` is `TRUNCATE`d and rebuilt every ingestion run, so any owned timestamp would reset to "this run." Deferred as a **T0013 rider, gated on the T0011 baseline**; fold into `research/deployment-research-plan.md` §4 when T0013 is drafted.
- **Hidden-salary honesty rule not reliably followed** (observed during T0009.8): the T0009.7 honesty rule explicitly says "say so plainly rather than claiming it is not in the data," but asking for the salary on a hidden-salary posting (`is_salary_negotiable = true`, `salary_min IS NULL`) reproducibly (2/2 attempts) returned "The salary information ... is not available in the data" — the exact phrasing the rule prohibits. Confirmed this is not a code/formatting bug (the table formatter renders raw column values only; `is_salary_negotiable` is passed through as-is) — it's the model not adhering to the prompt wording. Candidate follow-up: add an explicit few-shot example to `system_prompt` showing the desired negotiable-salary phrasing, or test with a lower-variance model/temperature setting.
- **`id`-in-SQL nudge is best-effort, not guaranteed** (T0009.11): `query_clean_jobs`'s SQL is model-generated, so `id` reaches a list result only if the model actually selects it — enforced via `config/prompts.yaml` `sql_generation` guidance ("always SELECT id as the first column when listing rows"), not deterministically. If the model omits `id` on some turn, `get_job_details` simply has no id to chain from that turn (the tool still degrades gracefully — "No posting found for id X" — for any id it is given, it just won't be given one). This is intentionally not "fixed" by rewriting the model's SQL to force-inject `id`, since that would blur the tool-boundary line between model-generated SQL and deterministic enforcement. Candidate follow-up: if omission proves frequent in practice, consider a few-shot example in `sql_generation` reinforcing the `id`-first convention.

### Query tooling & SQL safety
- ~~**[HIGH] SQL validator does not enforce a single table**~~ **Fixed by T0010.3** (2026-07-02): `sql_validator.validate_sql` previously only checked `"clean_jobs" in statement.lower()` (substring presence), so a query that *also* referenced another table passed — e.g. `SELECT * FROM clean_jobs JOIN raw_jobs USING (source, external_id)`. Now masks string-literal contents, then requires every `FROM`/`JOIN` table reference to equal `clean_jobs` and rejects a comma-separated `FROM` list; a bare `SELECT 1` (no table reference) remains valid. String-literal masking was initially scoped to this table check only; the same masking was later reused to fix the denylist keyword false-positive class (bug 4, `Code_Review_Notes.md`, resolved below). Detail: `Code_Review_Notes.md` bug 1.
- ~~**[MED-HIGH] Blocking LLM call on the async event loop**~~ **Fixed by T0010.4** (2026-07-02): `query_clean_jobs` (async) offloads the DB call via `asyncio.to_thread` but ran `generate_sql`'s `model.invoke(...)` synchronously on the loop, so each Groq SQL-gen round-trip blocked every concurrent request and the health probe. Now `sql = await asyncio.to_thread(generate_sql, question)` — scheduling-only change, `generate_sql`'s internals and the generated SQL are unchanged. Detail: `Code_Review_Notes.md` bug 2.
- ~~**[MED] "Showing N of M" can understate the true match count**~~ **Fixed by T0010.5** (2026-07-02): see § Resolved for the fix. Detail: `Code_Review_Notes.md` bug 5.
- **[LOW] No "here are the N you asked for — more exist" hint on an honored explicit count** (found during T0010.7): when a user explicitly asks for a specific count (e.g. "top 3") and more than 3 matches actually exist, `resolve_bounds` honors the requested `LIMIT` exactly and the answer reads "Found 3 result(s)" with no indication that additional matches exist beyond the 3 shown — technically correct (3 rows were genuinely returned and displayed) but could read as "there are only 3" to the user. Explicitly out of scope for T0010.7 (non-goal: no such hinting). Candidate follow-up: detect this case (fetch `requested + 1` instead of exactly `requested` when honoring an explicit count) and add a soft hint, e.g. "Showing the 3 you asked for — more may match."
- **[LOW] Nested SQL-generation call uses thread-offloaded sync `invoke`, not native async** (found 2026-07-03, discussion of T0010.4's fix): `generate_sql` (`src/agents/tools/query_clean_jobs.py:34-42`) is a synchronous function that calls `model.invoke(...)` (blocking network call to Groq); `query_clean_jobs` offloads it via `await asyncio.to_thread(generate_sql, question)` (T0010.4). This is correctness-safe — the event loop is never blocked — but it parks a thread-pool worker for the duration of every SQL-generation round-trip instead of yielding control natively. `AgentProvider().build_model()` returns a LangChain `BaseChatModel` (Groq), which supports `ainvoke` natively, so this is a low-risk, no-new-dependency change (`async def generate_sql`, `await model.ainvoke(...)`, drop the `asyncio.to_thread` wrapper). Not a bug, just less scalable under concurrent load than true async I/O. Candidate follow-up: convert `generate_sql` to `async def` using `model.ainvoke`.

### Evaluation harness (T0011.3)
- **[HIGH] Agent model `qwen/qwen3.6-27b` leaks raw `<think>...</think>` reasoning into message `.content`** (found running the live harness against real Groq, 2026-07-04): both the nested `generate_sql` LLM span's output and, on some turns, the agent's own final synthesis message came back with the model's raw chain-of-thought reasoning inline in `.content` (verbatim `<think>` block, then the real payload — or, on some turns, nothing usable after it). Two concrete symptoms observed: (a) the "SQL" `generate_sql` returns is sometimes the *entire reasoning transcript*, not a bare `SELECT` statement — this would fail `validate_sql` / read as garbage SQL in production, not just in eval; (b) on at least two live single-turn goldens (A3, C3) the agent's **final answer came back as an empty string** after multiple `query_clean_jobs` calls, suggesting the ReAct loop didn't cleanly converge to a clean assistant-facing message with this model/wrapper combination. This is a **model-behavior/config risk in the shipping agent**, not an eval-harness bug — `qwen/qwen3.6-27b` was picked in T0011.1's judge spike for *judge* JSON-reliability (GEval-only), not validated against the agent's own tool-calling loop; `config/settings.yaml:4` also pins it as the **agent** model (T0011.1 Known_Issues entry already flagged this residual as "not yet live-validated against the agent's tool loop" before the T0011.5 baseline — this is exactly that risk materializing). Candidate follow-up: check whether `ChatGroq`/langchain-groq surfaces qwen's reasoning in a separate field (e.g. `additional_kwargs["reasoning_content"]`) that should be stripped before `.content` is used, or whether a `reasoning_effort`/format param suppresses the `<think>` block entirely; re-validate before T0011.5 calibrates thresholds, since a reasoning-polluted or empty answer will tank every seam-3 metric regardless of true agent quality.
- **[MED] `deepeval==4.0.7`'s `ArgumentCorrectnessMetric` and `TaskCompletionMetric` are broken for this project's use** (found running the live harness): both raise `MetricTemplateInterpolationError: '<var>' is undefined` from internal Jinja templates — `ArgumentCorrectnessMetric` fails with `'stringified_tools_called' is undefined` whenever `tools_called` is non-empty (passes fine on a no-tool-call case, e.g. D1/D2's refusal path), and `TaskCompletionMetric` fails with `'tools_called_formatted' is undefined` unconditionally (reproduced on D1 and D2 alike, zero tools called). Root cause is internal to the pinned `deepeval` version — the metric's Python code passes a template context key that doesn't match what its own bundled `.txt`/`templates.json` prompt references — not anything in our test-case construction (confirmed by varying `tools_called` contents/emptiness with no change in outcome). `evals/harness.py::score()` isolates each metric's `.measure()` call so one broken metric doesn't blank the others for that seam; the T0011.3 baseline will show `Argument Correctness`/`Task Completion` as `None` with the raw error captured, for essentially every case.
