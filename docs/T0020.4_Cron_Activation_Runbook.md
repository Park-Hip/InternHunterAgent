## 3. D6 — adopt Neon into Alembic, then migrate it to head

> ### ⚠ CORRECTION (2026-08-09) — the original instruction here was **`alembic stamp head`. Do not
> run it.**
>
> This section assumed Neon's schema already matched the Alembic head, making `stamp` (record the
> version,
> touch nothing) the safe choice and `upgrade` the reckless one. **The assumption is false.** A
> direct query
> against production on 2026-08-09 returned:
>
> ```
> actual_count  expected_count  missing                                     unexpected
> 19            22              {first_seen_at, is_active, last_seen_at}     {}
> ```
>
> Neon's `clean_jobs` is exactly the **baseline** schema (`f3a1c9d2e7b4`) — nothing unexpected, and
> precisely
> the three T0019.3 lifecycle columns absent. The lifecycle migration `b7e2f4a91c3d` has **never run
> against
> production**; Neon was built by `pg_dump | psql` from a pre-migration sandbox (T0018.4) and has
> been frozen
> there since.
>
> **Why `stamp head` would have been destructive rather than merely wrong:** it writes
> `alembic_version = head`
> while the three columns stay missing. Alembic would then consider production current, so a later
> `alembic upgrade head` becomes a **no-op** — the correction path silently disappears. Production
> would be
> permanently three columns short with no migration that would ever add them, and nothing would
> report a
> problem. The failure is quiet and self-concealing, which is what makes it worse than an error.
>
> `stamp` is the right verb only when the physical schema already matches the revision you name.
> Here it
> doesn't, so the correct move is: stamp the revision Neon **actually is**, then upgrade forward
> normally.
>
> **How the instruction came to be wrong — it didn't start that way.** At T0019.2, `head` *was*
> `f3a1c9d2e7b4`: that ticket's own manual checks record `alembic upgrade head` producing a
> `clean_jobs` with
> "**all 19 columns**" and `alembic stamp head` resolving to `f3a1c9d2e7b4` (`Completion_Reports.md`
> → T0019.2,
> checks A and C). `stamp head` was correct as written. It silently expired when T0019.3 added
> `b7e2f4a91c3d` and moved `head` forward one revision. **The defect is naming a moving label in a
> procedure
> that outlives it** — which is why the corrected steps below pin the explicit revision hash.
>
> **Rehearsed against a faithful replica (2026-08-09)** — a scratch Postgres built to baseline,
> seeded, and
> with `alembic_version` emptied to match Neon's never-stamped state. Running the *old* instruction
> on it:
>
> ```
> alembic stamp head    → Running stamp_revision -> b7e2f4a91c3d
> alembic current       → b7e2f4a91c3d (head)      ← reports healthy
> alembic upgrade head  → (no migration runs)
> column count          → 19                        ← still broken, permanently
> ```
>
> Note the second line: **the old §3's own verification step — "expect `alembic current` to show the
> head
> revision with `(head)`" — passes.** D6 would have been signed off with production stranded and no
> error
> anywhere. A verification that cannot fail is not a verification.

**Use the direct, non-pooled Neon host** — migrations must never run through the `-pooler` hostname
(`research/archive/deployment-research-plan.md`). Run once, deliberately, in this order.

**3a — stamp the baseline** (the revision Neon physically is; writes only the `alembic_version`
row).
**First confirm Neon really is unstamped** — `alembic current` must print *nothing*. Anything else
means the
DB is not in the state this procedure assumes; stop and re-check before writing a version row.
```
ALEMBIC_DATABASE_URL="postgresql+psycopg://<user>:<pw>@<neon-DIRECT-non-pooled-host>/<db>?sslmode=require" uv run alembic current   # expect: empty
ALEMBIC_DATABASE_URL="postgresql+psycopg://<user>:<pw>@<neon-DIRECT-non-pooled-host>/<db>?sslmode=require" uv run alembic stamp f3a1c9d2e7b4
```
- `alembic current` before stamping: **empty — no revision recorded** ✅ (2026-08-09)

> **Footgun:** if `ALEMBIC_DATABASE_URL` is unset, `alembic/env.py:24` falls back to
> `settings.DATABASE_URL`
> and you will migrate **localhost** instead, with no error. The tell is a command that returns
> instantly with
> no SSL handshake delay. Keep the variable on every invocation.

**3b — pre-flight the backfill. This is a hard stop, not a sanity check.** `b7e2f4a91c3d` backfills
`first_seen_at`/`last_seen_at` from `raw_jobs.fetched_at` via an **inner** join (`UPDATE clean_jobs
c … FROM
raw_jobs r WHERE r.source = c.source AND r.external_id = c.external_id`), so any `clean_jobs` row
without a
matching `raw_jobs` row keeps the `server_default now()` — landing at *migration time*, i.e. looking
freshly
ingested. Locally the join was total (0 orphans, T0019.3); confirm the same on Neon **before**
upgrading:
```sql
SELECT count(*) FROM clean_jobs c LEFT JOIN raw_jobs r ON r.source = c.source AND r.external_id = c.external_id WHERE r.id IS NULL;
```
- Orphan rows: **0 of 50** ✅ (2026-08-09) — the join was total on Neon, as it was locally

> **Why this is load-bearing — measured, not theorised (2026-08-09 rehearsal).** `/ready` reports
> `MAX(last_seen_at)`, so orphan damage is **not proportional**: a *single* unmatched row sets the
> date for the
> whole corpus. In the rehearsal, 4 rows with exactly 1 orphan produced:
>
> | | value |
> |---|---|
> | what `/ready` would report | `2026-08-09` (migration day) |
> | truthful answer (`MAX(raw_jobs.fetched_at)`) | `2026-07-14` |
> | rows actually claiming today | 1 of 4 |
>
> **The failure looks identical to success.** You migrate, curl `/ready`, see today's date, and
> conclude the
> fix worked — while actually reading the migration's own timestamp. There is no signal
> distinguishing the two
> after the fact. If this count is non-zero, stop and decide explicitly what date those rows should
> carry
> before running 3c.

**3c — upgrade to head** (adds the three columns + runs the backfill):
```
ALEMBIC_DATABASE_URL="postgresql+psycopg://<user>:<pw>@<neon-DIRECT-non-pooled-host>/<db>?sslmode=require" uv run alembic upgrade head
```
