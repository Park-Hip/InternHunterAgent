## Query tooling & SQL safety
- **[HIGH] SQL validator does not enforce a single table. Fixed by T0010.3** (2026-07-02): `sql_validator.validate_sql` previously only checked `"clean_jobs" in statement.lower()` (substring presence), so a query that *also* referenced another table passed — e.g. `SELECT * FROM clean_jobs JOIN raw_jobs USING (source, external_id)`. Now masks string-literal contents, then requires every `FROM`/`JOIN` table reference to equal `clean_jobs` and rejects a comma-separated `FROM` list; a bare `SELECT 1` (no table reference) remains valid. String-literal masking was initially scoped to this table check only; the same masking was later reused to fix the denylist keyword false-positive class (bug 4, `Code_Review_Notes.md`, resolved below). Detail: `Code_Review_Notes.md` bug 1.
- **[MED-HIGH] Blocking LLM call on the async event loop. Fixed by T0010.4** (2026-07-02): `query_clean_jobs` (async) offloads the DB call via `asyncio.to_thread` but ran `generate_sql`'s `model.invoke(...)` synchronously on the loop, so each Groq SQL-gen round-trip blocked every concurrent request and the health probe. Now `sql = await asyncio.to_thread(generate_sql, question)` — scheduling-only change, `generate_sql`'s internals and the generated SQL are unchanged. Detail: `Code_Review_Notes.md` bug 2. (Superseded by the T0012.8 native-async change, below.)
- **[MED] "Showing N of M" can understate the true match count. Fixed by T0010.5** (2026-07-02): `table_formatter.format_rows` used to set `row_count = len(rows)` — rows the SQL returned, already capped by whatever `LIMIT` the *model* wrote — so when the model's `LIMIT` was below the real match count, the tool reported "Found N result(s)" as if N were the total and never surfaced a truncation notice. Fixed the Option-A way: the fetch bound is now system-owned, not model-owned. `query_clean_jobs` rewrites the validated SQL via `src/services/query/row_bound.py::enforce_fetch_limit` to fetch `agent.query.max_rows + 1` rows regardless of any `LIMIT`/`OFFSET` the model wrote, and `format_rows` uses the +1 row as a truncation sentinel (`TableArtifact.truncated: bool`) instead of trusting `len(rows)` as a true total. The answer now says "Showing the first N results — there are more matches. Narrow your search…" when truncated, and "Found N result(s)" only when N is genuinely the full match count; no exact total is computed for list queries (rejected Option B: a separate `COUNT(*)`). `COUNT(*)`/scalar queries are unaffected. Verified via `tests/services/query/test_row_bound.py`, updated `tests/services/query/test_table_formatter.py`, and updated `tests/agents/tools/test_query_clean_jobs.py`. Detail: `Code_Review_Notes.md` bug 5.
- **[LOW] Nested SQL-generation call uses thread-offloaded sync `invoke`, not native async. Fixed by T0012.8** (2026-07-06): `generate_sql` (`src/agents/tools/query_clean_jobs.py`) is now `async def` and calls `await model.ainvoke(...)` directly; `query_clean_jobs` calls `await generate_sql(question, config)` with no thread hop. The `execute_validated_sql` `asyncio.to_thread` offload (genuinely-sync DB work) is unchanged. Scheduling-only change — the generated SQL, prompt, and model are byte-for-byte the same. `test_generate_sql_runs_off_the_event_loop_thread` (which asserted the old thread-offload behavior) was removed since that behavior is precisely what this fix eliminates; `GenerateSqlContentCoercionTests` was converted to `unittest.IsolatedAsyncioTestCase` with `fake_model.ainvoke = AsyncMock(...)`.

## Evaluation harness (T0012.2)
- **[RESOLVED] qwen `<think>` reasoning leak — two distinct root causes, both fixed** (found/fixed 2026-07-06, closes the T0011.3 HIGH entry above): confirmed live against real Groq that the leak had two separate causes, not one.
  - **(a) SQL-span leak**: `generate_sql`'s raw response was the entire chain-of-thought transcript (verified live: 4166-char `<think>...</think>` block, no bare `SELECT`). Root cause: `ChatGroq`/`langchain-groq==1.1.2` inlines qwen's reasoning into `.content` by default. Fixed by forwarding a new `agent.groq.reasoning_format: hidden` config value (`config/settings.yaml`) into `ChatGroq(...)` in `src/agents/runtime/provider.py::build_model()` (one `groq_cfg.get("reasoning_format")` call, `None`-safe — no behavior change when unset). Confirmed live post-fix: `generate_sql("Which companies have AI Engineer roles?")` returns a bare `SELECT id, company FROM clean_jobs WHERE role ILIKE '%AI Engineer%'`, no `<think>` text.
  - **(b) Empty final-answer symptom (A3/C3) is a *different* bug, not the leak**: live experiment proved `reasoning_format='hidden'` alone reproduces the empty-`.content` symptom — with `agent.groq.max_tokens` at its old value of `1024`, a direct `model.invoke(...)` call returned `content=''` with `usage_metadata={'output_tokens': 1024, 'output_token_details': {'reasoning': 1024}}` — i.e. reasoning consumed the *entire* completion-token budget before any visible answer could be emitted, leaving nothing after hidden reasoning is stripped. This is the same root cause already recorded under T0011.6 for Gemini (`gemini-2.5-flash` truncating GEval JSON) — a thinking model's `max_tokens` must cover reasoning *and* the visible answer, not just the answer. `reasoning_format='hidden'` alone does **not** fix this: hidden reasoning still consumes completion tokens, it just isn't surfaced in `.content`. Fixed by raising `agent.groq.max_tokens` from `1024` to `2048` (`config/settings.yaml`) — confirmed live: the same probe with `max_tokens=2048` returned non-empty, coherent `.content`, and `generate_sql` against the real prompt returned clean bare SQL.
  - **Live end-to-end (A3 "Which jobs use Python?" / C3 "Do you have any COBOL jobs?") could only be partially verified**: Docker Desktop was not running in this sandbox, so the live app Postgres (`localhost:5433`) was unreachable (`psycopg.ConnectionTimeout`) — both goldens' final answers came back as a graceful, clean, **non-empty**, `<think>`-free "I ran into a database error" message (proving the fix holds through the full `AgentRuntime`/ReAct pipeline), but the actual data-bearing answer content for A3/C3 was not confirmed against real rows. Candidate follow-up: re-run `PYTHONUTF8=1 uv run pytest evals/test_three_seams.py -k "A3 or C3"` (or the same golden questions via `AgentRuntime`) once Docker/Postgres is up, to confirm the data-bearing answer text itself (not just leak-freeness).

## Earlier resolved (pre-register / chronological)
- **[MED] Explicit user-requested counts were silently overridden by the system cap. Fixed by T0010.7** (2026-07-02): T0010.5 made the fetch bound fully system-owned by stripping *any* model-written `LIMIT`, which fixed the "Found 20" honesty bug but as a side effect also discarded a genuine user-requested count (e.g. "top 3" always returned up to `max_rows` results with a truncation notice, never exactly 3). Fixed by making `LIMIT` a trustworthy signal of explicit user intent: `config/prompts.yaml` `sql_generation` now tells the model to add `LIMIT` only when the user explicitly asked for a specific count (previously "Always include a LIMIT clause"). `src/services/query/row_bound.py::enforce_fetch_limit` is replaced by `resolve_bounds(sql, max_rows) -> FetchBounds`, which parses the trailing `LIMIT` value and honors it exactly when `<= max_rows` (fetch and display exactly that count, no truncation notice); otherwise it falls back to the existing `max_rows + 1` sentinel fetch with `display_cap = max_rows`. `query_clean_jobs` passes `bounds.sql` to the executor and `bounds.display_cap` to `format_rows`. `COUNT(*)`/scalar queries are unaffected. Verified via rewritten `tests/services/query/test_row_bound.py` and a new honored-count test in `tests/agents/tools/test_query_clean_jobs.py`; the existing unbounded-truncation test is unchanged.
