# The database owns the agent column boundary

> **Status:** Active · **Decided:** 2026-10-19

## Context

`validate_sql` rejects the five hidden ingestion and lifecycle columns by name.
`SELECT * FROM clean_jobs` names none of them, so it passed the validator, and `internhunter_agent` held table-level `SELECT` on all 21 physical columns (#722, evidence E8 in #702).
The result carried `source`, `external_id`, `posted_date`, `first_seen_at`, and `last_seen_at` to the model even though the prompt's column contract says they do not exist.

A token check cannot see a star, an alias (`c.*`), a subquery, a CTE, a whole-row reference (`SELECT clean_jobs`), or a JSON conversion (`to_jsonb(clean_jobs)`).
Revoking only the hidden columns while the table-level grant remains does not help: table-level `SELECT` implies every column.

## Decision

`internhunter_agent` holds column-level `SELECT` on exactly the 16 declared columns and no table-level `SELECT`.
PostgreSQL is the column boundary; `validate_sql` remains the SQL-shape filter (single statement, `SELECT` only, allowlisted table, denylisted verbs and functions, explicit hidden-column names).

- A new physical column is invisible to the agent until a migration grants it.
- Making a column visible is a contract change: the grant, the prompt's schema context, the fixture projection, and this reference change together.
- The boot guard probes every hidden column and refuses to serve if any is readable, in addition to the visible-read and write-refusal probes.

## Alternatives rejected

- **Expand `*` against the 16 columns.** It needs relation-aware parsing for aliases, CTEs, and subqueries, and it still leaves whole-row and JSON forms open.
- **Reject `SELECT *` in the validator.** It needs structural analysis to catch `c.*` and nested star, and `SELECT clean_jobs`, `to_jsonb(clean_jobs)`, and `row_to_json(clean_jobs)` bypass it.
- **Revoke only the hidden columns.** A table-level `SELECT` still implies them, so the leak survives; the table-level grant must be revoked first.

## Consequences

- A table rebuild drops the grants, and the boot guard turns that into a refused boot instead of a broken first request.
  `docs/how-to/operate.md` owns the re-grant sequence.
- A `SELECT *` generated by the model now fails as `rejected` with an actionable detail, rather than returning hidden data.
  The prompt's tool-error rule already covers it.
- The evaluation harness still binds the agent DSN to the fixture owner, so offline captures do not exercise the boundary; #730 tracks that follow-up.
- Column-level privileges do not affect the writer role, which owns the table and keeps writing the hidden columns.

## Rollback

Run `alembic downgrade -1` to restore table-level `SELECT`, after deploying the previous revision or accepting that the stronger boot guard will refuse the downgraded grants.
Grant changes only; no data is migrated.
